## Q1 ultralytics YOLO-pose 自定义关键点：怎么定义、有什么硬限制、能不能一个模型输出多套点

### 结论（可执行）

1. **定义方式**：整套关键点集合由数据集 YAML 里的一个全局量 `kpt_shape: [N, 2|3]` 决定（2 = 只有 x,y；3 = x,y,visibility）。标签文件每行格式为
   `<cls> <cx> <cy> <w> <h>` + N 组 `<x> <y>`（或 `<x> <y> <v>`），全部归一化。
   可选字段：`flip_idx`（水平翻转时左右点的镜像映射，长度必须等于 N）、`kpt_names`（**按类别**写关键点名字，仅命名/展示用）、`kpt_oks_sigmas`（长度必须等于 N，全为正）。
2. **硬限制**：`kpt_shape` 是**数据集级 / 模型级单一值**，与类别无关。所有类别共享同一个 N。
   → **一个 ultralytics pose 模型不能同时输出"人体 17 点 + 手 21 点 + 绳子若干点"三套不同结构**。要拿到这三种结构，只有两条路：
   - **（推荐）拆成多个模型**，每个模型一套 `kpt_shape` / 一套权重 / 一套 `flip_idx`，再做后融合；
   - **（可行但有代价）并集 + 零填充**：`kpt_shape = [N_总, 3]`，每个实例只填自己那套点位，其余点写 `0 0 0`（visibility=0）。这在本框架里是**真能训**的——见下面源码证据——但要求第二维必须是 3（必须有 visibility），`flip_idx` 要按并集长度写，val 的 OKS 语义会被污染，且类别与点集子集的对应关系全靠模型自己学。
3. **更硬的约束（对本项目最关键）**：ultralytics pose **每个实例都必须有 bbox**（检测头与 pose head 共享同一批实例）。它就是"框 + 框内固定 N 点"，**没有"只有点、没有框"的原生表达**。绳子交叉点这类无框目标必须人为造框（例如绳段 bbox，或给单点类一个固定尺寸的小方框）。
4. 未发现关键点数量的硬上限（源码只校验 `kpt_shape` 的格式，不校验大小）——这点我标为**「未找到明确上限」**而非"无上限"。

### 依据

- **[官方文档]** `kpt_shape` 注释为 "number of keypoints, number of dims (2 for x,y or 3 for x,y,visible)"，并注明 "required for pose datasets"；`flip_idx` 用 5 点人脸示例解释左右镜像；`kpt_oks_sigmas` 明确写"长度必须等于 `kpt_shape` 的 N，且每个值必须为正；省略时 `[17,3]` 用 COCO sigmas，其它一律用均匀 `1/N`"——**这一条本身就证明框架只认单一 N**。
  <https://docs.ultralytics.com/datasets/pose.md>
- **[仓库]** 官方数据集配置里三者并存：`kpt_shape: [17, 3]`、`flip_idx`（17 个元素）、`kpt_names`（写成 `0:` 下挂 17 个名字，"Keypoint names per class"）：
  <https://raw.githubusercontent.com/ultralytics/ultralytics/main/ultralytics/cfg/datasets/coco-pose.yaml>
- **[仓库·源码级证据]** `Pose` head 只吃一个 `kpt_shape`：`self.kpt_shape = kpt_shape`、`self.nk = kpt_shape[0] * kpt_shape[1]`，输出通道数由它决定，**完全没有 per-class 分支**：
  <https://raw.githubusercontent.com/ultralytics/ultralytics/main/ultralytics/nn/modules/head.py>
- **[仓库·源码级证据]** 数据侧只做格式校验（`kpt_shape` 必须是 `[N, 2|3]` 列表，否则报错），不做"每类不同 N"的支持：
  <https://raw.githubusercontent.com/ultralytics/ultralytics/main/ultralytics/data/dataset.py>（约 112–116 行、207 行）
- **[仓库·源码级证据]** 并集+零填充为何能训：loss 里 `kpt_mask = gt_kpt[..., 2] != 0 if gt_kpt.shape[-1] == 3 else torch.full_like(..., True)`，`KeypointLoss` 用 `kpt_loss_factor = kpt_mask.shape[1] / (sum(kpt_mask != 0) + 1e-9)` 乘上 `kpt_mask`——**visibility=0 的点不进位置 loss，并按每实例可见点数重新归一**；另有 `kpts_obj_loss = bce_pose(pred_kpt[...,2], kpt_mask)` 作为"点存在性"分支：
  <https://raw.githubusercontent.com/ultralytics/ultralytics/main/ultralytics/utils/loss.py>
- **[issue]** 官方维护者原话（多类别、每类不同点数）：「`kpt_shape` 应该取**总点数**（car 4 + person 6 = 10）；缺的点写 `0 0`，两种写法都有效」，并强调"所有对象的关键点顺序必须一致"：
  <https://github.com/ultralytics/ultralytics/issues/3356>（正文见 API：<https://api.github.com/repos/ultralytics/ultralytics/issues/3356>）
- **[issue]** 自定义关键点集合的官方答复（改 `kpt_shape` + 相应调 `flip_idx` + 只保留感兴趣的点 + 标注里只留这些点）：
  <https://github.com/ultralytics/ultralytics/issues/9761#issuecomment-2040629148>
- **[官方文档]** CVAT 侧的官方格式说明把"多套骨架/单一 kpt_shape"讲得最清楚：「Pose: Skeletons」；`kpt_shape` 第一个数是骨架点数，**"如果有多个骨架点数不同，取最大的那个"**，小的骨架用 `0.0 0.0` + `visibility = 0` 补齐；并注明"坐标超出 [0,1] 的标签会被 YOLOv8 框架忽略"：
  <https://raw.githubusercontent.com/cvat-ai/cvat/develop/site/content/en/docs/dataset_management/formats/format-yolo-ultralytics.md>
- **[官方文档]** 结果接口确认"每实例固定 K 点 + 实例框"：`result.keypoints.data` 形状 `(N,K,2/3)`，`result.boxes` 是这些点所属实例：
  <https://docs.ultralytics.com/tasks/pose.md>

### 对本项目的含义

- **必须拆模型**：人体（17 或自定义 N1）/ 手（21）/ 脚（自定义 N3）/ 绳（自定义 N4）各训一个 `-pose` 权重，外加一个融合层（同名点做空间匹配 + 概率乘积或加权）。这与"多层模型逐级定位"的原始设计一致，不是退让。
- 若想省一个权重，可以把"手 + 脚"合成一个模型（都是"肢体末端 + 框"），但**不要把人体和绳子塞进同一个 pose 模型**：绳点的 bbox 是人造的、OKS 语义与人体完全不可比，并集方案会让 val 指标失去意义。
- 绳段/交叉点的 bbox 必须在标注规范里定义清楚（例：一个绳段实例 = 该段两端点连线的外接框；一个交叉点实例 = 以交点为中心、边长约图像短边 2–4% 的方框）。**这条一旦开始标 1 万张就很难改**。
- `kpt_oks_sigmas` 建议自定义：COCO sigma 是为人眼/人体尺度设计的，手部点和绳子点应该给更小的 sigma，否则 OKS 会被躯干点主导。

## Q2 "只有点、没有框"的路子：还有哪些，怎么比较

### 结论（可执行）

- **要"任意类别地标点 + 每点一个类别概率"，范式上最贴的是"每类每点一张热图（heatmap / belief map）"**，不是 YOLO-pose。YOLO-pose 的类别在**实例级**（一个框 = 一个类），一个实例内部所有点共享类别；它的 visibility 分支只是一个"该点是否存在"的 BCE 分数，不是"该点属于哪一类"。
- 具体选择建议（按 6 GB + ultralytics 生态 + 现成权重三项权衡）：
  1. **人体 / 手 / 脚** → 多个 `yolo11n-pose`（或 `yolo26n-pose`、`yolov8n-pose`），从 COCO-pose 权重迁移。理由：实现成本最低、生态现成、每类一模型天然绕开"单一 N"限制。
  2. **绳段 / 交叉点** → 不要用 YOLO-pose 硬塞；用 **CenterNet 式多通道热图小模型**（每类点一张图，另加"点类别分类"头），或 **MMPose 自定义 metainfo + heatmap/SimCC 头**。理由：不要求 bbox，天然支持"点集 + 每点类别概率"，且 6 GB 下 resnet18/mobilenet 级 backbone 在 640–768 完全可行。
  3. **手、脚趾这类小目标** → 若精度不够，改**两段式**（先检测器出实例框，再框内 ROI 回归 21/10 点）。二次元上的直接证据：BPD 论文里 Mask R-CNN 迁移（框内回归路线）OKS@50 = 0.7584，而 OpenPose（自底向上）只有 0.4922。
- **DOPE** 的思路（对"对象语义关键点"用 belief map，允许非解剖点）可借鉴，但它是为 6-DoF 位姿 + PnP 设计的，需要目标 3D 模型，**不能直接拿来当 2D 点检测器**。

### 对本项目的含义

- 用户要的"带分类概率的点列"，**在人体/手/脚这三层其实不需要逐点类别**（一个手实例的所有 21 点当然都是"手"的点），所以 YOLO-pose + 每点 visibility 分数基本够用。
- **只有绳子层真正需要"任意类别点 + 每点类别概率"**（绳段端点、交叉点、结，可能是不同类、且同类多点、且无框）。这一层建议独立于 ultralytics 生态，走 CenterNet/MMPose 热图路线；这样也顺带解决"没有框"的问题。
- 6 GB 的现实约束决定了"不要试图训一个大而全的多任务模型"：多个 n 级小模型串行推理，显存和迭代速度都更友好。

## Q3 二次元姿态估计的已有工作：数据集/模型/论文与可复现性

### 结论（可执行）

- **能直接拿来跑的只有一条线**：ADD（AnimeDrawingsDataset，2016）→ BPD（Bizarre Pose Dataset，WACV 2022）。BPD 是 4000 张、17 个 COCO 关键点 + bbox 的二次元单人全身数据集，附代码与权重（Google Drive），作者明确给出模型与用法。
- **但它们的手/脚粒度不够**：ADD 的 21 个具名关节里，手只有 `wrist` + `thumb`，脚只有 `ankle` + `tiptoe`；BPD 则统一到 COCO 17 点，最差的关键点就是 `wrist`（OKS@50 = 0.7341）。**没有任何手指/脚趾级标注。**
- **标注来源都是人工**：ADD 由志愿者人工标（README 致谢）；BPD 是在 ADD 基础上人工补标眼睛/耳朵、删掉 57 张多人物或非全身图，再加 2043 张"特意挑背面/复杂腿臂姿势"的人工标注。**不是从 3D 合成数据蒸馏**（Khungurn 等人另有 100 万帧 MMD 合成数据，但**未公开**）。
- 检索到的其它"动漫数据集"多数与姿态无关：AnimeRun 是 2D 动画**对应/光流**数据集（由开源 3D 电影转制），AnimeCeleb 是**头部**重演数据集（用 3D 动画模型采样）。Danbooru 系（booru_yolo）只做到躯干部件 bbox，作者自己写明"不做 COCO 式复杂关键点"。

  <https://raw.githubusercontent.com/dragonmeteor/AnimeDrawingsDataset/master/README.md>
- **[API实测] ADD 的真实关节名单**（我下载了 `data/data.json`，2000 条，每条 21 个具名点）：
  `body_upper, neck, head, nose_tip, nose_root, arm_left, elbow_left, wrist_left, thumb_left, arm_right, elbow_right, wrist_right, thumb_right, leg_left, knee_left, ankle_left, tiptoe_left, leg_right, knee_right, ankle_right, tiptoe_right`
  <https://raw.githubusercontent.com/dragonmeteor/AnimeDrawingsDataset/master/data/data.json>
- **[论文] BPD / Chen & Zwicker, WACV 2022**（CVF 开放版 + arXiv 全文）：
  - 数据集：**4000 张**带全部 17 个 COCO 关键点与 bbox 的插画角色图，划分 3200 / 313 / 487；补标缺失的眼/耳关键点使用"开源 COCO 标注器"；另外 **2043 张**新样本专门挑背面与复杂姿势（背面相关 tag 占比从 5.45% 提到 21.25%）。
  - 方法：领域侧用 Danbooru 迁移的 ResNet50 tagger（837k 图 / 1062 类）作 backbone，任务侧用 COCO keypoints 预训练的 Mask R-CNN；输出 **25 张热图 = 17 COCO 点 + 8 个附属肢体中点**。

  <https://www.openaccess.thecvf.com/content/WACV2022/html/Chen_Transfer_Learning_for_Pose_Estimation_of_Illustrated_Characters_WACV_2022_paper.html>
  <https://arxiv.org/html/2108.01819v3>（摘要页：<https://arxiv.org/abs/2108.01819>）

### 对本项目的含义

## Q5 绳缚/绳子元素检测：可借鉴的工作与输出形式差距

### 结论（可执行）

- **最接近我们需求的是机器人领域的"DLO（可变形线状物体）感知"**，其中 **HANDLOOM（CoRL 2023）** 与我们的目标几乎同构：
  - 任务：把一条 **trace（有序点序列）** 拟合到线缆灰度图上，并**同时分类交叉（crossing）**；
  - 数据：30,000 个**模拟**样本 + 568 个**真实**样本，且**公开了带 GT trace 的标注数据集**；
  - 结果：多缆 trace 80% 正确率；单缆含结的 trace/结识别 77%；泛化到未见过的结型/材料（橡胶、布绳）85%。
  - 输出形式 = **有序点列 + 交叉分类**，与"点列"目标一致，**不是 bbox**。
- **但迁移性存疑**：HANDLOOM 的域是机器人半平面场景的灰度线缆图，且"每个交叉最多 2 段"。**能否迁移到二次元插画未证实**（我无法打开其项目页/PDF 验证细节，见下）。
- 工业/电力线方向检索到的工作，输出多为**分割掩码/线状目标**，不是交点，且域差更大（多数未亲自打开验证，标未证实）。
- **输出形式差距总结**：
  | 想要的 | 现有工作给的 | 差距 |
  |---|---|---|
  | 绳段：有序点列 | 分割/中心线（可转点列，如 HANDLOOM 的 trace） | 小，可转换 |
  | 交叉点：带类别概率的点 | trace 上的 over/under 分类，或线检测+后处理求交 | 中，需要自己定义"交点类别"与输出头 |
  | 结：点/位置 | HANDLOOM 的结识别（分类，不是定位） | 大，定位需自研 |
- **二次元绳缚专门工作：检索未发现**（本报告未找到任何该题材公开数据集/论文），标为「检索未发现」而非"不存在"。

### 依据

- **[论文/会议] HANDLOOM: Learned Tracing of One-Dimensional Objects for Inspection and Manipulation**，Viswanath et al., CoRL 2023, PMLR v229:341-357。摘要原文关键句："estimating the spatial state of long deformable linear objects such as cables, threads, hoses, or ropes"；"fits a **trace** to a greyscale image of cables"；"we evaluate HANDLOOM on semi-planar DLO configurations where **each crossing involves at most 2 segments**"；"trained with 30,000 simulated examples and 568 real examples to **autoregressively estimate traces of cables and classify crossings**"；"Supplementary material, including all code and an **annotated dataset of RGB-D images of cables along with ground-truth traces**"。
  <https://proceedings.mlr.press/v229/viswanath23a.html>（PDF：<https://proceedings.mlr.press/v229/viswanath23a/viswanath23a.pdf>，本环境不支持抓 PDF）
- **[论文]** UniStateDLO: Unified Generative State Estimation and Tracking of Deformable Linear Objects Under Occlusion（arXiv:2512.17764，2025-12）：DLO 状态估计/跟踪，明确针对遮挡、状态空间高维、缺乏显著视觉特征；输出为"状态（点/参数化）"而非 bbox。<https://arxiv.org/abs/2512.17764>
- **[论文·未证实]** Caporali 等，*Robotic perception and manipulation of deformable linear objects: A survey*（IJRR）：搜索结果中出现的 PDF（<http://webdiis.unizar.es/~glopez/papers/CaporaliIJRR2026.pdf>）与 Sage 镜像（<https://sage.cnpereading.com/doi/10.1177/02783649261432253>）。**本环境不支持 PDF，内容细节未证实**，仅作为"该方向有系统性综述"的线索。
- **[论文·未证实]** CVF-DLO: Cross-Visual-Field Branched Deformable Linear Objects Route Estimation（IEEE 2025，<https://ieeexplore.ieee.org/document/11063326>）：仅在搜索结果中出现，**未打开验证**。
- **[检索结果·未证实]** 电力线/线缆工业检测类数据集（如 ArcGIS Power Line Classification、电力线 LiDAR 数据集）输出以分割/线状目标检测为主，**未逐一验证**。
- **[检索实证]** arXiv 全文检索 `all:"rope" AND all:"keypoint" AND all:"detection"`、`all:"cable" AND all:"keypoint detection"` 返回的多是 DLO 操作/状态估计工作，没有"绳子交叉点关键点"这一类任务定义。

### 对本项目的含义

- 绳层的标注与建模建议（自研为主）：
  1. **绳段**：一个实例 = 一段绳（有序点列 + 若需 bbox 则取外接框），类别 = 绳段；
  2. **交叉点**：单点实例，**类别至少分 2 类（上压 / 下压）**，这是二次元绳缚里语义最重的信息，也正是 HANDLOOM 那种"crossing 分类"的直接类比；
  3. **结**：单点或小框 + 类别。
- 不要期待分割模型直接给出"点列"；HANDLOOM 式的"自回归 trace 拟合"才是最贴合的技术形态，但需要（a）绳的中心线/掩码监督，（b）序列化标注格式。**如果标注工具不支持"有序点列"，绳段的顺序信息就会在标注阶段丢失**——这点必须和 Q6 的工具选择一起决定。
- 绳层完全可以用热图（每类一张图）来同时表达"段端点/交叉点/结"，无需框——与 Q2 的结论一致。

## Q6 标注工具的现实约束：Make Sense 到底行不行

### 结论（可执行）

- **Make Sense 不能标关键点/骨架，也不能导出可用于 YOLO-pose 的点标注。用户当前选定的 `https://makesense.bimant.com/` 不适合本项目。** 硬证据（源码级 + 官方 README）：
  1. 标注类型只有 5 种：`IMAGE_RECOGNITION(打标签) / POINT / RECT / POLYGON / LINE`——**没有 skeleton/pose 类型，也没有"点属于哪个实例"的分组概念**（一个 Point 只有 `point` + `labelId`）。
  2. 导出矩阵：**Point 行只有 CSV 打勾**，YOLO / VOC XML / VGG JSON / COCO JSON 全部不支持（Line 也只有 CSV；Rect 支持 YOLO/VOC/CSV；Polygon 支持 VGG JSON/COCO JSON）。
  3. 点导出实现只有一个 CSV 分支，字段固定为：`label_name,x,y,image_name,image_width,image_height`（像素坐标、四舍五入取整）。
- **直接后果**：即使把 21 个手指点全部点出来，CSV 里也**没有手实例 id、没有点的顺序保证**；多只手/多个绳结的图会糊在一起，无法生成 ultralytics pose 行（pose 行必须有 `bbox + 固定顺序的 N 点`）。
- **若坚持用 Make Sense（不推荐）的补救路径**：用 POINT 标、把关键点身份编进 label 名（如 `hand_L_thumb_tip`），另外用 RECT 手动给每个实例画框（Make Sense 里点与框**没有父子关系**），导出 CSV + YOLO 框，再写脚本按"label 名 → 顺序索引"拼行。**多实例图会歧义，成本高、易错**。
- **替代工具（能标具名关键点，且能直接导出 YOLO-pose）**，按推荐度：
  1. **X-AnyLabeling（本地，首选）**：官方文档写明流程 = 画 `Rectangle`（设 label + `group_id`）→ 用 `Point` 画关键点并填**同一个 `group_id`**；缺失点可省略、遮挡可勾 `useDifficult`；导出菜单直接有 `Export YOLO-Pose Annotations`，需上传按类别列关键点名的 `pose_classes.yaml`（还支持 `has_visible`）。GPL-3.0，10.6k star，2026-10 仍活跃。
  2. **CVAT（本地/自托管或在线）**：有专门的 **Skeleton** 标注类型（点可命名、可设属性/occluded/outside，可连边），skeleton 自带外接框；导出格式里有官方 **Ultralytics YOLO（Pose，`kpt_shape:[N,3]` + visibility）** 与 **COCO Keypoints**。**坑**：① 任务/项目建好后**不能改 skeleton 配置**（要先想清楚点集）；② 不同 skeleton 点数不一致时按最大 N 补 `0.0 0.0` + `visibility=0`；③ 坐标超出 `[0,1]` 的标注会被 ultralytics 忽略；④ 点是 skeleton 的子元素，不能单独存在。
  3. **Label Studio**：有 `KeyPoint` / `KeyPointLabels` 标签；**COCO 与 YOLO 导出都支持 KeyPointLabels**（官方导出文档里直接给出了 pose 行示例）。**坑（两个必做步骤）**：① 每个 `<Label>` 必须写 `model_index` 定义点的顺序；② 必须再配一个 `<RectangleLabels>` 作为父框，并把每个关键点在 Regions 面板里**拖到对应矩形下面**建立 `parentID`，否则导不出。另外社区版导出是同步的，大项目容易撞 90 s 超时（要用 SDK 快照导出）。
  4. **Roboflow（云）**：Keypoint Detection 项目，需先设 keypoint skeleton；点有 Visible / Occluded / Deleted 三态（对应 2/1/0）。**数据要上传云端**（本项目题材敏感，需先评估）。其导出格式清单里"YOLOv8 Pose"的确切命名**未证实**（我没能打开其格式列表页）。
  5. （备选）**COCO Annotator**（`jsbroks/coco-annotator`，MIT，2.3k star，2025-01 有提交）：BPD 论文作者**就是用"开源 COCO annotator"补标关键点的**（论文原文），间接说明它支持 COCO 关键点标注；我**未亲自验证其 UI**。

## Q7 6 GB 显存下的可行配置

### 结论（可执行）

- **官方没有公开"某模型在某分辨率下的显存占用表"**：维护者答复原话是 "we don't have exact memory specifications publicly available"。所以不要等官方数字，**用官方 AutoBatch 让框架自己测**。
- 官方给的三条硬机制（直接可用）：
  1. 单卡 `batch=-1` → 自动 profile 并按 **约 60% 显存** 选 batch；`batch=0.70` → 指定比例；
  2. **首个 epoch OOM 时自动把 batch 减半并重试，最多 3 次**（仅单卡；DDP 下直接报错）；
  3. `amp=True` 默认开启（CUDA 上会先做一次能力检查，失败回退 FP32）。
- **保守可跑配置建议**（针对 6 GB + 竖图 720×1200 + 小目标点，属推荐而非实测数值）：
  ```bash
  # 第一轮：让 AutoBatch 探底
  yolo pose train model=yolo11n-pose.pt data=anime_pose_hand.yaml \
      imgsz=640 batch=-1 amp=True cache=False workers=2 device=0 epochs=200
  # 若探出的 batch 太大/太小，改用固定值：
  yolo pose train model=yolo11n-pose.pt data=... imgsz=640 batch=8 amp=True \
      cache=False workers=2 optimizer=auto patience=50
  ```
  - `imgsz`：竖图长边信息量大，**先 640 跑通链路，再试 768**（显存约 ×1.44）；手指/脚趾点很小，640 下可能不可辨，768 往往值得。
  - `batch`：n 级 pose（2.6–2.9 M 参数）在 640 下从 **8** 起步比较稳；OOM 就 4。
  - `amp=True`、`cache=False`（或 `'disk'`）、`workers` 2–4（Windows 上必须把训练代码放进 `if __name__ == "__main__":`，且多卡 DDP 在 Windows 官方不支持）。
  - `pretrained`：**一定要从 COCO-pose 权重迁移**（`yolo11n-pose.pt`），别从 YAML 从零训。
  - 显存再紧时的兜底：`imgsz=512`、`freeze` 前若干层、降低 `mosaic`（mosaic 会拼 4 图，峰值显存更高）。
- 模型选择：当前官方文档主推 **YOLO26 Pose**（`yolo26n-pose`：640 下 **2.9 M 参数 / 7.6 GFLOPs**；COCO mAP50-95 57.2）；YOLO11n/YOLOv8n 级 pose 权重仍在包内可用（文档仍引用 YOLOv8n/YOLO11n）。**若从零开始，建议直接 `yolo26n-pose` 或 `yolo11n-pose`，n 级都是 6 GB 友好档**。

### 依据

- **[官方文档]** `batch` 的三种模式（整数 / `-1` 约 60% 显存 / `0.70` 比例）与 **OOM 自动减半重试最多 3 次（仅单卡）**，以及 `amp` 默认 True：
  <https://docs.ultralytics.com/modes/train.md>
- **[官方文档]** 训练最佳实践："batch=-1 profiles the model and picks a batch size targeting roughly 60% memory utilization"；"If you encounter memory errors, reduce the batch size incrementally"；混合精度默认开启：
  <https://docs.ultralytics.com/guides/model-training-tips.md>
- **[issue]** 官方**没有**公开显存规格（维护者/机器人答复原话）；提问者环境为 GTX 1070 8 GB + 16 GB RAM，跑 `yolo11n-pose` imgsz=640 batch=1 时报内存不足（但该 issue 的根因是重复加载模型/Windows 内存，**不能当作"n-pose 跑不动 8 GB 卡"的证据**）：
  <https://github.com/ultralytics/ultralytics/issues/16813>
- **[issue·实测数据点]** AutoBatch 的 profiling 输出（A100-80G，**YOLOv8L-seg**，imgsz=640）：batch=1 → **1.726 GB**，batch=4 → 5.352 GB，batch=8 → 10.127 GB，batch=16 → 19.623 GB；维护者解释 AutoBatch 目标比例从 YOLOv5 的 80% 降到 67% 是因为小显存卡用户反馈 OOM，且 EMA/val 会额外吃显存：
  <https://github.com/ultralytics/ultralytics/issues/1659>
  （**注意**：这是 L-seg 的数字，**不能线性外推到 n-pose**；n-pose 显著更小，但具体值需自己用 `batch=-1` 实测。）
- **[官方文档]** 模型规模（`yolo26n-pose` = 2.9 M 参数 / 7.6 GFLOPs / COCO mAP50-95 57.2；文档同时仍引用 YOLOv8n、YOLO11n 的机型限定说明）：
  <https://docs.ultralytics.com/tasks/pose.md>
- **[官方文档]** `channels_last` 在 Windows 默认关闭、多卡 DDP 在 Windows 官方不支持、`cache` 的显存/内存权衡：
  <https://docs.ultralytics.com/modes/train.md>

### 对本项目的含义

- 6 GB 足够训 n 级 pose；**瓶颈不是模型，而是标注产能与数据管线**。真正的风险是"人手 21 点 + 脚 10 点 + 绳点"的训练集标注量（10,300 张图人工标这些点是本项目最大的成本项）。
- 建议先用 `batch=-1` 跑 1 个 epoch 把 AutoBatch 的 profile 表打印出来（它会给出各 batch 的 `GPU_mem`），把这份真实数字记录进实验日志，再定固定 batch——这比照抄任何社区数字都可靠。
- 既然是多模型融合，训练时**串行训、串行推理**（6 GB 一次只加载一个模型）；推理端若需要同时加载，优先用 ONNX/FP16 导出以压显存。
